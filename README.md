# Jenkins

pipeline is the root block of a Declarative Jenkins Pipeline. Everything related to the pipeline configuration, agent, tools, environment, stages and steps is defined inside this block. Here I'm specifying the Jenkins agent where the pipeline should execute. I'm using the label executor-1, so Jenkins schedules this pipeline on a node having that label. That agent needs to have the required tools and permissions because the actual shell commands like Maven, Docker and Trivy will execute there. Under the tools section, I'm telling Jenkins to use the Maven installation configured in Jenkins with the name devmaven. This helps keep the Maven version controlled rather than depending on whatever happens to be available on the agent. I'm defining the ECR repository as an environment variable so I can reuse it across different stages. That makes the pipeline easier to maintain and avoids hardcoding the complete ECR repository path multiple times. The first stage cleans the Jenkins workspace. I do this to make sure the build starts with a clean working directory and doesn't accidentally use files left behind by a previous build. Next, I check out the application source code from our Git repository. Jenkins places the repository contents into the workspace, and the following Maven and Docker stages work against that checked-out source. Here Jenkins performs the Maven build. clean removes the previous build output and package compiles and packages the Java application, producing the JAR under the target directory. Since I'm not passing -DskipTests here, the configured Maven tests can also run as part of the lifecycle. withSonarQubeEnv tells Jenkins to use the SonarQube server configuration named sonar for this analysis. Inside the SonarQube environment, I run Maven through the verify phase and invoke the SonarQube analysis goal. The project key identifies this application in SonarQube, so the analysis results are associated with the devproject project. In this current hands-on pipeline, the build and Sonar analysis are separate stages, so Maven lifecycle execution happens again during the Sonar stage. In a production pipeline I'd optimize this to avoid unnecessary repeated work, depending on how the project's Sonar configuration is integrated. After sending the analysis to SonarQube, I wait for the quality gate result. I have abortPipeline: true, so if the project doesn't satisfy the configured quality gate, Jenkins stops the pipeline instead of continuing toward artifact or image publication. Because analysis by itself doesn't enforce anything. The quality gate gives us a pass or fail decision based on the quality conditions we've configured. By making the pipeline wait for that result and abort on failure, we prevent code that doesn't meet the required quality standards from progressing further in the CI pipeline. Paralle block potentially reduces pipeline execution time when the two operations don't depend on each other. The Nexus branch publishes the generated application artifact to our Nexus repository. This gives us a centralized location for storing and versioning build artifacts. Here Jenkins builds the Docker image using the Dockerfile in the workspace. I tag the image with the ECR repository name and the Jenkins build number, which gives me a unique image tag for each build. The dot at the end means the current workspace is used as the Docker build context. After building the image, I scan that exact image using Trivy. I'm filtering the output to HIGH and CRITICAL severity vulnerabilities and saving the results into a text report. This gives us a security validation step before the image is pushed to ECR. I archive the Trivy report in Jenkins so the vulnerability scan result is retained with the corresponding build. That gives us a record we can refer back to later. Before pushing to ECR, the Jenkins agent needs AWS permissions to interact with the ECR repository. In our setup, the agent's AWS identity or IAM role is used for that authentication rather than hardcoding credentials into the Jenkinsfile. Finally, I push the image that was built and scanned to the ECR repository using the same build-number tag. So the exact image that passed the CI and security checks is the image stored in ECR.
